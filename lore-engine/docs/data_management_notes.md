# Data Management 笔记（用本项目的真实例子讲）

> 写给非专业读者。这份文档不讲抽象理论，而是用 lore-engine 里 GS1 数据的**真实文件和真实问题**，把几个数据管理（data management）的核心概念讲清楚。每一节都是：**一个概念 + 我们项目里的例子 + 为什么这么做**。
>
> 背景：我们把各种攻略文本整理成结构化 JSON（`data/gs1/*.json`）。最近做 locations（地点）时，绕不开这些概念，正好拿来当教材。

---

## 0. 一句话地图

做 locations 时我们有两个文件，分工要分清：

| 文件 | 是什么 | 谁来写 |
|---|---|---|
| `data/gs1/locations.json` | 38 个地点的**名册**（名字、类型、章节、别名）| **人手写**，稳定 |
| `data/gs1/location_refs.json` | 「每个地点有哪些 djinn/怪物/装备…」的**索引** | **脚本生成**，随时可重建 |

下面六节解释：为什么是两个文件、为什么一个手写一个生成、脚本到底在解决什么问题。

---

## 1. 源数据 vs 派生数据（source vs derived）

**概念**：有些数据是「原始事实」，必须有人来记、是唯一的真相来源（source of truth）；另一些数据是从原始事实**算出来**的（derived）。算出来的东西不该当成独立真相去维护——否则两边会打架。

**本项目的例子**：
- 「Flint 这个 djinn 在哪？」——这是**源数据**，记在 `djinn.json` 里：`"location": { "area": "World Map (near Vale)" }`。每个实体自己记自己在哪。
- 「World Map 这个地点上有哪些 djinn？」——这是**派生数据**。它不是新事实，把所有 djinn 的 location 字段倒过来看一遍就能算出来。

**为什么重要**：如果我们既在每个 djinn 里记位置，又在每个地点里手写一份「这里有哪些 djinn」，那就是**同一个事实记了两遍**。哪天改了 djinn 的位置却忘了改地点那边，数据就自相矛盾了（这叫 update anomaly，更新异常）。

**我们的做法**：locations.json 不存这份反向清单。它交给脚本去算，算完放进**另一个**文件。

---

## 2. 物化视图（materialized view）

**概念**：派生数据有两种用法——(a) 每次要用时现算；(b) 预先算好存下来，直接读。后者叫**物化视图**（materialized = 把临时结果落成实体文件）。物化的好处是读得快、能被静态浏览（甚至能让 AI 直接读）；代价是数据一变就得重新生成。

**本项目的例子**：`location_refs.json` 就是一个物化视图。它把「现算」的反向索引预先算好存下来：

```json
"mercury-lighthouse": {
  "djinn": ["fizz", "sleet"],
  "bosses": ["saturos"],
  "items": ["..."]
}
```

这样想知道「水星灯塔有什么」，直接读这一段就行，不用每次去扫 8 个 JSON 文件做关联。

**为什么这么选**：lore-engine 的目标是**可查询的知识库**，还要能喂给 LLM 直接读。所以「预先算好存成文件」比「每次现算」更合适——这正是物化视图的典型适用场景。但我们守住一条铁律：**物化视图绝不手改**，永远用 `python scripts/locations_refs.py` 重新生成。文件头里也写了这句警告。

---

## 3. 受控词表 + 实体解析（controlled vocabulary + entity resolution）

**概念**：真实世界的数据是**脏**的——同一个东西，不同人有不同拼法。要把它们归到同一个「标准名」，需要两样东西：一张**受控词表**（标准名 + 所有已知的别名/异名），和一套**实体解析**逻辑（把脏字符串对到标准名上）。这在数据领域也叫 record linkage（记录连接）。

**本项目的例子**（这是 locations 最核心的工作）。各个 JSON 里同一个地点的写法五花八门：

| 脏写法（来自不同攻略）| 标准地点 |
|---|---|
| `Bibilin Cave`（拼错）| `bilibin-cave` |
| `Atmiller Cave`（拼错）| `altmiller-cave` |
| `Tolbi-bound Boat` / `Ship` | `tolbi-bound-ship` |
| `Crossbone Isle #1` … `#10` / `Ghost Ship` | `crossbone-isle` |
| `Colosso` / `Babi's Palace` / `Battle Arena` | `tolbi` |

我们的受控词表就是 `locations.json` 每条里的 `name` + `aliases`：

```json
{ "id": "bilibin-cave", "name": "Bilibin Cave", "aliases": ["Bibilin Cave"] }
```

脚本读这张表，把任何出现的脏字符串解析回 `id`。**遇到新的脏写法，不改脚本，只往 `aliases` 里加一条，再重跑。**

**一个真实的硬骨头**：装备的位置常常一串写好几个地方，还夹着怪物名：

```
"Babi Lighthouse / Tunnel Ruins / Venus Lighthouse (Chimera Mage)"
```

这一条要同时算到 3 个地点。所以解析逻辑分三步：① 整串精确匹配 → ② 按 `/ ; ,` 拆开、并剥掉 `(...)` 括注（括号里是怪物名，不是地名）逐段匹配 → ③ 词边界子串兜底。一条记录可以落到多个地点（多匹配），这是对的。

---

## 4. 单一真相源 & 规范化 vs 反规范化

**概念**：
- **单一真相源（single source of truth）**：每个事实只在一个地方权威地存着。
- **规范化（normalization）**：不重复存数据，避免矛盾。
- **反规范化（denormalization）**：为了读得快，**故意**复制一份冗余数据——但必须清楚它是派生的、可重建的。

**本项目的例子**：`location_refs.json` 其实是**反规范化**的产物（地点和实体的关系，在实体侧已经存了一遍，这里又按地点存了一遍）。我们之所以敢这么做，是因为守住了三个条件：

1. 它和源数据**物理分开**（独立文件），一眼能看出哪个是源、哪个是派生。
2. 它由脚本**确定性重建**，不手改。
3. 谁是老大很明确：**实体侧的 location 字段才是真相**；`location_refs.json` 只是它的倒影。

对比一下被否决的方案：把反向索引直接塞进 `locations.json` 每个地点里。那样手写数据（地名、简介）和生成数据（索引）混在同一个文件，每次重跑都改写这个文件，时间一长就分不清哪行是人写的、哪行是机器写的——这违反了「源/派生分层」。

---

## 5. 引用完整性 + 数据质量报告

**概念**：**引用完整性（referential integrity）**指数据里的「指针」都得指向真实存在的东西——不能有悬空引用。**数据质量报告**则是构建过程顺手吐出的「哪里不对」清单，让你**看见**数据有多脏，而不是默默掩盖。

**本项目的例子**：脚本 `locations_refs.py` 跑完会做双向检查 + 打一份报告：
- 每个被索引到的实体 id，在它的源文件里真的存在吗？每个地点 id 真的存在吗？（引用完整性）
- **未匹配报告**：任何解析不到标准地点的脏字符串，全部列出来。

第一次跑，报告吐出 10 条未匹配。逐条看，全都讲得通：
- 9 条是怪物的 `B2` / `B3`——这是「地下 2 层 / 3 层」的楼层碎片，而这些怪物的位置列表里**已经**有 `Altin Peak` 了，所以 `B2`/`B3` 是多余碎片，加进忽略名单。
- 1 条是 game-ticket 的 `Various shops / Mimics`——游戏点券哪家店买东西都可能掉，本来就不是某个具体地点，也忽略。

处理完，未匹配从 **10 → 0**。

**关键心法**：报告不是用来「清零就完事」的，而是**逼你逐条理解数据**。`fizz` 这个 djinn 我本以为该在 Imil（它跟 Mia 一起加入），但数据把它解析到了 `mercury-lighthouse`（Mia 实际加入的地方）。脚本忠实反映了源数据——**这正是它的价值：不替你美化，让你看见真相**。

---

## 6. 幂等构建 + 先量化再改源（measure before you mutate）

**概念**：
- **幂等 / 确定性（idempotent / deterministic）**：同样的输入，跑一次和跑十次，结果**一字不差**。这样你才敢随时重跑，不怕越跑越乱。
- **先量化再改源**：想清理源数据之前，先用工具**测量**它到底有多脏；别凭感觉就动手改原始文件。

**本项目的例子**：
- 脚本里所有输出都**排了序**（地点按 id 排、每个实体清单去重再排序）。所以重跑两次，`location_refs.json` 的 md5 完全一样——我们用这个验证「幂等」。
- 关于「要不要清理源数据」：理想的数据模型里，每个实体的位置应该是一个**外键**（直接存 `location_id: "kolima"`），而不是自由文本 `"Kolima"`。但要不要现在就动手把 6 个实体文件全改成外键？我们的决定是**先不改**——先把上面那份未匹配报告做出来，**量化**源到底多脏（结论：只有 10 条边角情况，且都能解释）。等真有需要再说。这就是「先量化，再改源」：不打没必要的大仗。

---

## 小结

我们就做了一件小事——给地点建反向索引——但它把数据管理的骨架全用上了：

1. 分清**源**（实体的 location）和**派生**（反向索引）。
2. 派生数据做成**物化视图**，单独存、脚本生成、不手改。
3. 用**受控词表（aliases）+ 实体解析**把脏写法归一。
4. 反规范化要守规矩：**源/派生分层、单一真相源**。
5. 构建时查**引用完整性**，并产出**数据质量报告**逼自己看清数据。
6. 构建**幂等可重跑**；改源之前**先量化**。

下次遇到「这份数据该放哪、该不该复制一份、该不该手填」的纠结，对照这六条基本就有答案了。
